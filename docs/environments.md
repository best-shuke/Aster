# 环境（Environment）

环境是一个独立的执行空间：它决定代理可用的技能、MCP 服务、工具权限和资源限制，并可以包含多个独立协作的成员代理。没有启用自定义环境时，程序保持原有的单代理行为。

- **环境定义**：可复用的 JSON 配置，位于程序目录 `environments/`、用户目录 `~/.agents/environments/` 或工作区 `.agent/environments/`。资源指纹与信任机制见 [架构](architecture.md)。
- **环境会话**：环境的一次运行实例。每个对话会话（`/new`、`/resume`）对应一个独立的环境会话；多代理环境的任务、消息、会议、成员上下文和事件都保存在会话里，会话之间默认互相隔离。

## 快速开始

```text
/env create research-team --template multi-agent   创建团队环境（默认写入用户目录并记录信任）
/env use research-team                              进入环境，开启新会话
/env skills                                         查看已选技能与可添加技能
/env skills add research                            添加技能；disable/enable/remove 管理
/env mcp                                            查看已选 MCP 服务与可添加服务
/env mcp add github --tools 'get_*,search_*'        引用已配置的服务，并限制工具
/env agents                                         查看成员
/env agents add statistician --description '统计分析' --tools read,grep,exec
/env limits max_meeting_rounds=2                    查看或修改资源限制
/env status                                         当前环境、成员、任务、协议
/env log 50                                         团队事件
/env results                                        成员后台完成的工作与发给主代理的结果
/env exit                                           退出环境，恢复默认代理
/multiagents                                        进入默认团队环境（不存在时自动创建）
```

编辑命令默认作用于当前环境，`--env 名称` 可指定其他环境。修改当前环境后会立即重新加载并保留对话。原有命令 `/env 名称 [keep] [--yes]`、`/env off`、`/env show|trust|deny 名称` 不变。若已有环境恰好与新子命令同名（如 `status`），用 `/env use 名称` 切换。

## 默认团队

`multi-agent` 是通用团队，适用于论文研究、资料调研、数据分析、写作、规划、资料整理及其他任务。
模板提供 8 名协作成员，主代理 `main` 根据用户目标协调分工、处理需要用户决定的事项并综合交付。

| 成员 | 职责 | 声明的工具能力 |
| --- | --- | --- |
| `researcher` | 调研、证据搜集、来源核对 | 读取、搜索；配置可用时联网搜索 |
| `analyst` | 数据、证据、方法、论证与备选方案分析 | 读取、搜索、写入、编辑、执行命令 |
| `planner` | 目标、方案、资源、任务依赖与完成标准 | 读取、搜索；配置可用时联网搜索 |
| `executor` | 资料整理、文件转换和具体工具操作 | 读取、搜索、写入、编辑、执行命令 |
| `writer` | 论文、报告、方案和其他内容的起草 | 读取、搜索、写入、编辑 |
| `editor` | 结构、表达、术语和格式的一致性编辑 | 读取、搜索、写入、编辑 |
| `fact-checker` | 事实、引文、参考文献与结论依据的独立核查 | 读取、搜索；配置可用时联网搜索 |
| `critic` | 质疑假设、比较解释、独立评审结果 | 读取、搜索 |

实际权限仍取环境与成员声明的交集，所有成员均可使用 `team`。角色提示词约定任务分工，
工具权限按上表授予；声明 `exec` 的成员仍能通过命令修改文件，不构成文件系统只读隔离。
主代理按任务选择成员，未收到消息或任务的成员保持空闲；默认团队的 8 名成员与 128 名成员上限分别计算。
通用模板显式开启动态创建：现有成员无法覆盖重要专业问题时，可按需创建方法学审阅者、统计分析者、
领域研究员或其他会话级专家。新成员继续受创建者工具权限和团队额度约束，创建本身不开始工作，
需要投递消息或分配任务。未显式配置 `dynamic_agents` 的其他环境仍默认关闭此能力。

成员可以直接求助、共同维护任务板、共享证据、讨论分歧并要求对方复核；主代理负责用户沟通和最终整合。
任务的检查方式随交付物确定：研究检查来源与论证，分析检查数据与计算，写作检查内容与格式，软件工作检查实现与测试。
角色提示词指导协作，具体分工仍由模型选择。

例如论文研究可先由研究员建立证据材料，分析员或按需创建的方法学专家独立审阅方法，规划员安排
后续研究，写作者据证据形成稿件，编辑员整理结构，事实核查员和评审员提出问题后交回相关成员修改。
文献摘要、论文全文、拟议实验和实际完成的实验须区分；引用和结果只能来自实际获得的材料。
全文、PDF、检索数据库及外部实验工具是否可用，取决于提供的材料和配置的工具。

模板在 `/env create 名称 --template multi-agent` 时复制。已有环境保留原成员和自定义配置；
`/multiagents` 对已存在的默认环境也不会覆盖。试用完整新团队可创建一个不同名称的环境：

```text
/env create full-team --template multi-agent
/env use full-team
/env agents
```

编程任务可选择 `coding-team` 模板，其中保留研究、架构、前端、后端、测试、安全、性能和交付评审八个角色。主代理的提示要求把单一、紧密耦合的交付物（一个网页、应用、游戏或模块）整体交给一名实现者（主代理自己或一名成员）编写并自检，只有文件独立、接口约定清楚的部分才拆给多人实现，其他成员负责评审或测试：

```text
/env create dev-team --template coding-team
/env use dev-team
```

## 定义文件

原有字段（`prompt_file`、`skills_dirs`、`mcp_config_file`、`inherit_mcp`、`inherit_skills`、`tools`、`worker_tools`、`role_prompts` 等）保持原义。新增字段均为可选，缺省时行为与之前一致：

| 字段 | 含义 |
| --- | --- |
| `type` | `single-agent`（默认）或 `multi-agent` |
| `skills` | 技能名 → 是否启用。存在时只启用其中为 `true` 的技能 |
| `mcp` | 服务名 → `true`/`false` 或 `{"enabled", "tools", "deny"}`；存在时只启用列出的服务，`tools`/`deny` 是工具名通配模式 |
| `agents` | 成员名 → 成员定义（仅 `multi-agent`） |
| `limits` | 资源限制，见下文 |
| `collaboration` | `protocols`（启用的协议）、`dynamic_agents`（是否允许运行时创建成员；缺省否，通用模板显式开启）、`broadcast`（是否允许 `all` 广播） |

成员定义字段：`description`、`instructions` 或 `prompt_file`（二选一）、`enabled`、`skills`（技能名数组）、`tools`（工具名数组）、`mcp`（服务名数组，或 服务 → 工具模式数组/`"*"`）、`write_paths`（允许写入的工作区相对路径）、`reasoning_effort`。

示例见 [examples/research-team.json](examples/research-team.json)；一次真实的多代理运行记录见 [多代理演示](multi-agent-demo.md)。

## 继承与覆盖规则

环境只能在进程启动时的能力范围内选择或收窄，不能扩大：

1. **工具**：环境 `tools.allow/deny` 收窄启动工具集；联网搜索与子代理上限不能超过启动设置。
2. **技能来源**：环境 `skills_dirs` → 启动技能（`inherit_skills` 为真时）→ 内置协作技能（仅在存在 `skills` 选择时作为来源）。同名技能以先出现的来源为准，用户技能总是覆盖内置技能。
3. **技能选择**：存在 `skills` 时只启用选中且为 `true` 的技能；技能仍按需加载——提示词只列名称、描述和位置，代理需要时读取全文。
4. **MCP 来源**：环境自己的 MCP 文件与启动 MCP 配置（`inherit_mcp`）合并，同名以环境为准；`mcp` 选择只在这些来源中按名称挑选并添加工具模式。
5. **成员能力 = 环境能力 ∩ 成员声明**：
   - 工具：未声明时只有只读工具（read、grep、find、ls、websearch）；`ask_user`、`monitor`、`update_plan` 始终只属于主代理；`team` 始终授予成员。
   - MCP：未声明时没有 MCP；声明后权限是环境 `mcp` 选择与成员声明的交集，两边的工具模式都必须满足。环境未启用的服务即使成员声明也不可用。
   - 技能：未声明时使用环境启用的全部技能；声明后只取其中环境已启用的部分。
6. **动态成员**：开启 `dynamic_agents` 后，成员可用 `spawn_agent` 创建会话级成员，其工具不能超过创建者自身的工具，且不授予 MCP。

## 凭据

环境定义不保存凭据。MCP 服务的令牌、密码和认证头继续使用原有机制：在 MCP 配置中写 `${环境变量}`，值来自进程环境或被 Git 忽略的 `.env`。`/env mcp add 名称 --command …|--url …` 新建环境专属服务时，认证头、看起来是凭据的环境变量与参数必须是 `${VAR}` 引用，URL 中不能内嵌用户名密码；该文件权限为 600。

## 多代理运行时

`multi-agent` 环境中，主代理（`main`）是用户的唯一对接者，同时也是团队成员；其他成员是真正独立的代理：

- 每个成员有自己的模型客户端、私有上下文（跨激活持久保存）、系统提示、工具集和预算。成员的系统提示以环境的基础提示词（默认 `system_prompt.md`，与主代理和 delegate 子代理相同）开头，再接角色说明与团队规则；这段公共前缀也让成员复用主代理的提示缓存。成员的生成循环复用主代理的 `TaskRuntime`（上下文压缩、输出恢复、限流、截止时间、取消）。
- **成员自检**：有 `exec` 的成员在一次激活中用 `write`/`edit` 改过代码文件（`.json`、`.yaml`、`.toml` 等数据文件不算），之后却没有通过的独立检查（测试、构建、断言；`node --test 路径`、`node --check 文件` 也算，不带文件的写法什么都不检查，不算）就要结束时，运行时提醒它一次；仍未检查时，它交付的最终消息末尾附上未经检查的说明及原因（检查失败后未重新通过，或最后一次修改之后没有检查），供主代理和评审者判断。提醒之后的请求若因预算、超时等失败，交付提醒前那条完整答复。只看成员自己的修改，队友同时修改、只运行检查而未改代码的成员（如测试失败的测试员）都不受影响；没有 `exec` 的成员无法运行检查，不提醒也不附说明。
- 成员之间直接通信，不经过主代理。主代理通过 `team action=wait` 接收回复、任务结果和协议结论。
- **调度**：投递到空闲成员的消息立即启动一次激活（独立线程）；成员忙碌时消息留在邮箱，下一次激活合并处理；超过并发上限的成员排队。
- **轮次与后台**：成员的工作随主代理处理用户请求的轮次开始。轮次结束时：
  - 交互会话（终端或通过标准输入逐行提问）中，仍在进行的工作转入后台继续：成员之间照常投递、唤醒和完成任务，直到团队空闲、达到显式设置的 `limits.background_seconds`（默认不限时，0 表示关闭）或用户发出下一条消息——下一轮直接接管仍在运行的激活，不重做。后台工作仍计入上一轮的预算与次数限制。
  - 单次命令（`agent "提示"`）、Esc/Ctrl-C 中断、后台时限到达、切换会话或环境、退出进程时，进行中的激活被取消、其输入重新排队，下一轮自动继续。
  - 后台期间底部状态栏显示工作中的成员与新结果数量；每个成员结束、以及团队空闲或暂停时，在输入框上方打印一行提示。`/env results` 查看后台期间各成员的报告和发给主代理的结果，但不消耗它们；下一轮先接管后台工作再生成“后台期间发生了什么”的提示（此后完成的工作属于本轮），主代理用 `team action=wait` 读取结果。
  - 本轮发起的工作仍在进行时，主代理的最终答复会被挡回，让它用 `team action=wait` 等成员完成，检查整合后的结果再交付；每次调用工具后再次提前答复会再次被挡回。连续两次直接答复（中间没有工具调用）时第二次被接受，以免模型连续被拒导致本轮失败；本轮进入最后的收尾时限后也不再挡回。用户明确要求不等待（如“不要等待”“不用等”“don't wait”“continue in the background”）时，或仍在进行的只是之前轮次留下的工作时，只提醒一次：交互会话中它可以选择不等待，并告知用户成员在后台继续。此时本轮结果记为“后台继续”而不是“已完成”：成员尚未完成的修改不要求在本轮验证，主代理自己改过的代码仍需在最后一次修改之后开始的独立检查通过；若成员恰在本轮结束前完成、没有工作转入后台，本轮记为“未完成”。可以转入后台的轮次中，成员的激活只受自身超时限制，不受本轮时限截断：轮次正常结束时转入后台继续，被中断时取消并重新排队。
- **义务结算**：成员一轮结束时的最终消息会作为它未显式处理的请求的回复、所分配任务的结果（标记为推断完成）以及协议轮次的发言。若它仍在等待他人（未获回复的请求、委派的任务、自己发起的协议）或邮箱里还有未读消息，这些义务顺延到之后的激活；若形成等待环（A 等 B、B 等 A）则立即结算以避免死锁。成员失败或预算耗尽时也会自动答复请求者，任何代理都不会无限等待。

### team 工具

| 类别 | 动作 |
| --- | --- |
| 成员与状态 | `list_members`、`get_state`（只含本代理可见的内容） |
| 通信 | `send_message`（`kind=request` 需要回复；`reply_to` 回复；`to` 可为成员、`main`、`group:<id>`、`all`）、`create_group` |
| 任务 | `create_task`（`assignee`、`depends_on`）、`update_task`、`get_task`、`request_review` |
| 产物与决策 | `share_artifact`（team/group/private 可见性）、`get_artifact`、`record_decision` |
| 协议 | `start_protocol`、`contribute`、`conclude` |
| 其他 | `load_skill`（只能加载授予自己的技能）、`spawn_agent`（需开启）、主代理专用 `wait`、`cancel` |

### 协作协议

协议是可选的。所有协议由同一个引擎在相同的邮箱、产物和决策之上运行，区别只在轮数、哪些轮次为盲轮（参与者互相看不到发言、彼此消息被阻止）以及是否由主持人总结：

| 协议 | 默认轮数 | 盲轮 | 总结 |
| --- | --- | --- | --- |
| `meeting` | 2 | 0 | 主持人 `conclude` |
| `debate` | 3 | 0 | 主持人 `conclude`，可用 `stances` 指定立场 |
| `brainstorm` | 2 | 1 | 主持人 `conclude` |
| `independent_research` | 1 | 1 | 运行时汇总全部发现交给发起者 |
| `review_decision` | 1 | 1 | 主持人 `conclude` |
| `coordinate_work` | 1 | 0 | 主持人 `conclude` 并创建任务 |

轮数受 `limits.max_meeting_rounds` 限制；全部参与者 `ready=true` 时非盲轮可提前结束。结论生成团队可见的产物，`decisions` 记录到决策板。

### 内置协作技能

`builtin/skills/` 提供 `team-collaboration`、`task-delegation`、`independent-debate`、`brainstorming`、`conflict-resolution`、`team-retrospective`，描述何时求助、何时先独立调查、何时正式讨论、如何解决分歧、如何并行与控制成本。它们只是可选策略：环境通过 `skills` 选择启用哪些，成员用 `load_skill` 按需加载。

## 安全与资源限制

| 限制 | 默认 | 作用 |
| --- | --- | --- |
| `max_concurrent_agents` | min(20, 启动子代理上限) | 同时运行的成员数 |
| `max_agents` | 128 | 成员总数（含动态成员），可显式提高到 1024 |
| `max_messages_per_turn` | unlimited | 每轮团队消息总数 |
| `max_activations_per_agent` | unlimited | 每个成员每轮激活次数 |
| `max_message_hops` | 100 | 消息链长度，阻止循环转发（回复不计入） |
| `max_meeting_rounds` | 32 | 单个协议的轮数上限；协议仍按自己的轮数正常结束 |
| `max_task_depth` | 32 | 任务嵌套深度，阻止无限委派 |
| `max_tool_calls_per_agent` | unlimited | 每个成员每轮工具调用 |
| `token_budget_per_agent` | unlimited | 每个成员每轮的非缓存 token：输入中未命中提示缓存的部分加输出；仍累计统计 |
| `activation_timeout_seconds` | unlimited | 单次激活时限；不能在后台继续的轮次同时受主任务时限约束 |
| `background_seconds` | unlimited | 交互会话中主代理答复后，成员可持续工作；0 表示轮次结束即暂停 |

上述六项工作预算在 JSON 中用 `null`、`"unlimited"` 或 `"none"` 表示不设上限，命令行用
`键=unlimited`。这与把数值调得很大不同：不会因为累计用量或经过的时间超过某个预算而暂停。
并发、成员容量、消息跳数、协议轮数和任务深度仍要求整数；达到并发上限的成员排队，已有工作继续执行。
`background_seconds=0` 保持原有的关闭后台语义，不能把所有字段的 `0` 都当作无限。

默认值用于定义中未显式配置的字段；已有环境写入的 `limits` 保留原值。运行 `/env limits`
查看当前环境的实际限制，用 `/env limits 键=值 …` 调整，或用 `键=default` 恢复该字段的默认值。
增大上限不会自动添加成员或启动任务；是否允许动态创建由环境的 `collaboration.dynamic_agents` 决定。并发仍受启动子代理上限约束，
生成仍受上下文窗口和适用的任务时限约束。更大的工作预算允许更多模型调用，实际用量取决于任务。

主任务总时限也默认不设上限。旧 `.env` 中已有的数字仍优先生效；持续任务可显式启动：

```sh
DEEPSEEK_MAX_TASK_SECONDS=unlimited DEEPSEEK_MAX_SUBAGENTS=20 agent
```

这些进程设置也可写入本机 `.env` 后重启。单次命令模式仍等待成员完成后结束；交互会话中可转入
后台的成员不受主代理当前轮次截止时间截断。每轮累计 token 预算与模型上下文窗口、单次输出上限
分别计算；网络空闲和单个外部操作的超时、模型服务配额、用户取消与进程退出仍按实际情况处理。

已有环境要采用上述全部额度，可在进入环境后执行：

```text
/env limits max_messages_per_turn=unlimited max_activations_per_agent=unlimited max_tool_calls_per_agent=unlimited
/env limits token_budget_per_agent=unlimited activation_timeout_seconds=unlimited background_seconds=unlimited
/env limits max_concurrent_agents=20 max_agents=128 max_message_hops=100 max_meeting_rounds=32 max_task_depth=32
```

其他边界：成员的文件工具不能访问环境状态目录、信任记录和主对话的会话文件（含原子写入的临时文件）；`write_paths` 可限制成员写入范围；代理之间看不到彼此的私信与私有上下文；同一环境会话同一时间只能被一个进程打开；状态文件绑定所属环境，跨环境加载会被拒绝；需要用户决定的事项由成员转交主代理，只有主代理能使用 `ask_user`。工具策略不是操作系统沙箱，`exec` 仍以运行用户的权限执行命令。

## 持久化与恢复

```text
<DEEPSEEK_ENVIRONMENT_STATE_DIR>/sessions/<来源-名称-路径摘要>/<会话ID>/
  state.json        共享状态：成员、邮箱、消息、任务、群组、产物、决策、协议、最近事件
  events.jsonl      完整事件日志
  agents/<成员>.json 每个成员的私有上下文
  lock              进程锁
```

每次状态变化都会持久化。进程中断后重新打开会话（`/resume`）时：进行中的激活输入重新排队并标记为“中断后重投”，已完成的任务、消息和决策原样保留；成员私有上下文中缺少结果的工具调用会补上“结果未知”的记录，提醒代理先核实实际状态再重复操作。

## 已知限制

- 后台工作只在进程运行期间进行；进程退出后剩余工作在下次打开会话的第一轮继续。
- **并发编辑**：成员直接写共享工作区。团队内所有代理（含主代理）共享一份编辑记录：某代理基于旧读取执行 `edit` 或整文件 `write` 时，若文件此后只被团队成员的文件工具改过，运行时把它的修改与最新内容按行三方合并，结果中的 `merged` 字段说明合并已发生；修改重叠时仍报 `file_changed`，代理需重新读取后再改。用户、`exec` 命令或其他程序造成的变更不会被自动合并，同样要求重新读取；单代理环境保持原有的读取版本检查。
- 预算与时限是协作式的：长时间的单个工具调用在其自身超时或取消前不会被打断。
- 代理行为由模型决定；运行时保证投递、调度、隔离和限制，但不保证模型选择了最优的协作方式。
